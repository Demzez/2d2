# 2D2 — README для демонстрационной базы PostgreSQL 15+

**Назначение:** локальная и учебная демонстрация личного кабинета абонента и панели администратора вымышленного мобильного оператора 2D2. Все имена, номера, суммы и платёжные операции в seed-данных — **тестовые**. Не используйте этот набор в production.

## 1. Файлы и требования

| Файл | Назначение |
|---|---|
| `telecom_schema.sql` | Исходная схема PostgreSQL 15+ с таблицами в схеме `telecom` (пользовательский исходный файл) |
| `telecom_seed_demo.sql` | Создаёт/дополняет тестовые данные, три учётные записи; обновляет пароль существующим демо-пользователям |
| `telecom_demo_fix_passwords.sql` | **Только** обновляет пароль трёх уже существующих демо-пользователей, без обновления остального наполнения |

Нужны PostgreSQL **15+**, созданная база данных (пример: `telecom`), права на схему `telecom`, INSERT/UPDATE необходимых таблиц и разрешение на временные таблицы. При новом запуске схема должна быть создана до seed.

## 2. Порядок запуска

### Если база пустая

```bash
# Создайте БД заранее, например: createdb telecom
psql -d telecom -v ON_ERROR_STOP=1 -f telecom_schema.sql
psql -d telecom -v ON_ERROR_STOP=1 -f telecom_seed_demo.sql
```

### Если seed запускался ранее и нужно обновить **только пароли**

```bash
psql -d telecom -v ON_ERROR_STOP=1 -f telecom_demo_fix_passwords.sql
```

### Если нужно повторно запустить всё наполнение

```bash
psql -d telecom -v ON_ERROR_STOP=1 -f telecom_seed_demo.sql
```

В обновлённом `telecom_seed_demo.sql` у существующих `demo.*` логинов обновляются только `password_hash` и `updated_at`, **при условии совпадения роли и e-mail**. Остальные основные сущности наполняются идемпотентно для демо-ключей. Скрипт рассчитан на отдельную тестовую БД; на новом календарном месяце могут быть добавлены новые помесячные события/начисления. Не применяйте его к настоящим клиентам. Для удалённой БД добавьте параметры `-h`, `-p`, `-U`.

`BEGIN` / `COMMIT` и `ON_ERROR_STOP=1` позволяют остановить заполнение при ошибке; проверяйте код завершения `psql`.

## 3. Учётные записи для входа

**У всех трёх пользователей один пароль: `1q2w3e4r5t`.**

| Роль | Логин | Пароль | Абонентский номер | Сценарий |
|---|---|---|---|---|
| `user` | `demo.alena` | `1q2w3e4r5t` | `+375291000101` | Положительный баланс, активный номер, тариф «Комфорт S» |
| `user` | `demo.maksim` | `1q2w3e4r5t` | `+375291000102` | Отрицательный баланс, административная блокировка, тариф «Комфорт M» |
| `admin` | `demo.admin` | `1q2w3e4r5t` | — | Администратор без строки в `subscribers` |

Пароль **не хранится открытым текстом** в БД. В `telecom.users.password_hash` для каждого логина записан **отдельный Argon2id-хеш с уникальной 16-байтной солью**. Его формат: `$argon2id$v=19$m=65536,t=2,p=1$<base64-соль>$<base64-ключ>` (параметры: память 64 MiB, 2 итерации, 1 поток, ключ 32 байта). Используется `base64.RawStdEncoding`, то есть без `=` на конце, как в Go:

```go
argon2.IDKey([]byte(password), salt, 2, 64*1024, 1, 32)
```

**Проверяйте** пароль пересчётом `argon2.IDKey` **с солью из сохранённого хеша** и сравнением ключей за постоянное время (`subtle.ConstantTimeCompare`). Не сравнивайте хеш с результатом нового вызова `hashPassword()` — тот генерирует новую случайную соль. Если сервер использует только SMS-авторизацию, добавление пароля в БД не создаёт endpoint логин/пароль автоматически.

**Безопасность:** общий простой пароль, включая администратора, допустим исключительно для изолированного демо-окружения. Не публикуйте такую БД в интернете; смените все пароли для любой более широкой среды.

## 4. Состав наполнения

- **Справочники:** 5 тарифов, 12 дополнительных услуг, в том числе архивные позиции. Исходные коды услуг и тарифов сохраняются; конфликтующие записи каталога не перезаписываются.
- **Учетные записи:** ровно 2 тестовых абонента и 1 тестовый администратор. По схеме один мобильный номер и лицевой счёт на абонента; администратор номера не имеет.
- **Подключения:** текущие услуги, история отключений, контакты.
- **Потребление:** сотни событий по метрикам `internet_mb`, `messenger_mb`, `minutes_own`, `minutes_other`, `minutes_roaming`, включая детализацию вызовов.
- **Финансы:** начисления по тарифам, услугам и сверхлимитному потреблению; счета за **два завершённых** месяца; начисления текущего месяца — без `invoice_id`. Учитывается НДС 20% в демонстрационных ценах; в `charges` цена без НДС и НДС хранятся отдельно.
- **Платежи:** `succeeded`, `pending`, `failed` с **фиктивными** провайдерскими идентификаторами; FIFO-распределение оплаченных сумм по старым счетам.
- **Оповещения:** информационные сообщения и предупреждения о балансе / расходовании услуг, прочитанные и непрочитанные.

Месяцы и временные метки рассчитываются относительно **даты выполнения** с использованием временной зоны **Europe/Minsk**. Денежные суммы указаны в **BYN**, интернет-трафик — в **МБ**, звонки — в **минутах**. Тарифы и цены — пример для вымышленного 2D2, **не** действующие предложения коммерческих операторов. Модель расчёта упрощённая: частичный месяц не тарифицируется пропорционально.

`auth_otps` и `auth_sessions` не заполняются. Одноразовые коды и реальные refresh-сессии должны создаваться сервером, а не seed-скриптом.

## 5. Проверка после запуска

```sql
-- Проверка всех трёх учётных записей и их ролей.
SELECT u.login, u.role, u.email, s.msisdn, s.account_number,
       s.balance_byn, s.is_blocked, s.admin_blocked
FROM telecom.users u
LEFT JOIN telecom.subscribers s ON s.user_id = u.id
WHERE lower(u.login) IN ('demo.alena', 'demo.maksim', 'demo.admin')
ORDER BY u.login;

-- Убедиться, что параметры всех хешей соответствуют Go-функции.
-- Не раскрывает сами хеши.
SELECT login,
       split_part(password_hash, '$', 2) AS algorithm,
       split_part(password_hash, '$', 3) AS version,
       split_part(password_hash, '$', 4) AS parameters
FROM telecom.users
WHERE lower(login) IN ('demo.alena', 'demo.maksim', 'demo.admin')
ORDER BY login;

-- Проверка, что итог счета совпадает с суммой строк начислений.
-- Ожидается 0 строк.
SELECT i.id, i.total_amount_byn,
       COALESCE(SUM(c.amount_byn + c.vat_byn), 0) AS charges_total
FROM telecom.invoices i
JOIN telecom.subscribers s ON s.id = i.subscriber_id
JOIN telecom.users u ON u.id = s.user_id
LEFT JOIN telecom.charges c ON c.invoice_id = i.id
WHERE lower(u.login) IN ('demo.alena', 'demo.maksim')
GROUP BY i.id, i.total_amount_byn
HAVING i.total_amount_byn <> COALESCE(SUM(c.amount_byn + c.vat_byn), 0);

-- Объёмы данных для двух абонентов.
SELECT u.login,
       (SELECT COUNT(*) FROM telecom.usage_events e WHERE e.subscriber_id = s.id) AS usage_events,
       (SELECT COUNT(*) FROM telecom.charges c WHERE c.subscriber_id = s.id) AS charges,
       (SELECT COUNT(*) FROM telecom.invoices i WHERE i.subscriber_id = s.id) AS invoices,
       (SELECT COUNT(*) FROM telecom.payments p WHERE p.subscriber_id = s.id) AS payments,
       (SELECT COUNT(*) FROM telecom.notifications n WHERE n.subscriber_id = s.id) AS notifications
FROM telecom.subscribers s
JOIN telecom.users u ON u.id = s.user_id
WHERE lower(u.login) IN ('demo.alena', 'demo.maksim')
ORDER BY u.login;
```

### Если вход не работает

1. Убедитесь, что сервер работает с таблицей `telecom.users` (schema / `search_path`) и ищет логин регистронезависимо, если это ожидается.
2. Проверьте, что сервер **разбирает соль и параметры из `password_hash`**; для новых хешей ожидаются `m=65536,t=2,p=1`, версия 19.
3. Убедитесь, что приложение действительно реализует вход **по логину и паролю**, а не только SMS.
4. Если в БД до изменений были другие пароли, запустите файл `telecom_demo_fix_passwords.sql` и повторите проверку параметров.
5. Проверьте, что роуты уведомлений (`/finances`, `/analytics`, `/profile`) соответствуют маршрутам фронтенда, а фактическая блокировка номера определяется как `is_blocked OR admin_blocked`.

## 6. Ограничения и статус проверки

Хеши для пароля `1q2w3e4r5t` рассчитаны Argon2id с **разными** солями и независимо проверены повторным вычислением. SQL-файлы проверены на наличие ожидаемых вставок/патчей и консистентность подстановок. **Реального прогона PostgreSQL и интеграционного теста Go-сервера здесь не было**; для полной проверки выполните seed и запросы выше в локальной БД, затем авторизацию по трём логинам.
