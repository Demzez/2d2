# 2D2 — REST API аналитического кабинета абонента

**Назначение:** подключение и мониторинг услуг телекоммуникационного оператора, просмотр тарифов, баланса, начислений и счетов, визуализация потребления, уведомления об отклонениях.

**Версия:** 1.0  
**Базовый URL:** `http://localhost:5555/api/v1`  
**Формат:** JSON, UTF-8.  
**БД:** PostgreSQL, схема `telecom` из `telecom_schema.sql`.  
**Принцип:** один пользователь — один телефонный номер и один лицевой счёт. Это сознательное упрощение для курсового проекта.

## 1. Общие правила

- Все закрытые методы требуют `Authorization: Bearer <access_token>`. Исключения: методы `/auth/*`, кроме того, что их токены передаются в теле, и подписанный webhook платежей.
- Время — ISO 8601 с часовым поясом (`2026-10-29T12:00:00+03:00`). Финансовые и месячные отчёты используют календарь `Europe/Minsk`.
- Фильтр `month` имеет формат `YYYY-MM`. Даты `from` и `to` — `YYYY-MM`, либо `YYYY-MM-DD` в тех методах, где это явно указано.
- Валюта — BYN. Все денежные суммы в JSON передаются **строками с двумя знаками** (`"23.46"`); в PostgreSQL — `NUMERIC(12,2)`.
- Объёмы интернет-трафика передаются в **МБ** (1024 МБ = 1 ГБ), длительность звонков — в **минутах**. В SQL это поля `quantity` и `quota_amount`; единица определяется `metric`.
- `id` — числовой идентификатор соответствующей записи. Нельзя передавать `subscriber_id` для доступа к чужому счёту: он извлекается сервером из проверенного access-токена.
- Возвращается `200` при успешном чтении/обновлении, `201` при создании, `202` при отправке SMS, `204` при удалении или обработке webhook. Ошибки: `400`, `401`, `403`, `404`, `409`, `422`, `429`, `500`.
- Общий вид ошибки:

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Некорректный номер телефона"
  }
}
```

Распространённые коды: `INVALID_CREDENTIALS`, `INVALID_OTP`, `OTP_EXPIRED`, `UNAUTHORIZED`, `NOT_FOUND`, `CONFLICT`, `NUMBER_BLOCKED`, `PAYMENT_UNAVAILABLE`. Пароли, OTP, refresh-токены и секреты webhook не должны попадать в логи.

## 2. Какие экраны покрываются

| Экран/действие | Методы API |
|---|---|
| Вход по паролю, вход по SMS, регистрация, выход | `/auth/login`, `/auth/otp/request`, `/auth/otp/verify`, `/auth/register`, `/auth/refresh`, `/auth/logout` |
| Главная: баланс, тариф, услуги, остатки, рекомендации | `/dashboard` |
| Список подключённых/доступных услуг, поиск, подключение/отключение | `/services`, `/services/{id}/connection` |
| Управление номером и смена тарифа | `/me`, `/number`, `/tariffs`, `/number/tariff` |
| Финансы: баланс, начисления, счета, платежи, детализация, пополнение | `/finance/summary`, `/finance/charges`, `/finance/invoices`, `/finance/invoices/{id}`, `/finance/payments`, `/finance/usage-details`, `/finance/topups` |
| Аналитика: звонки, структура расходов, интернет по дням, популярные услуги, календарь | `/analytics` |
| Любимые собеседники | `/favorites`, `/favorites/{id}` |
| Значки уведомлений и сообщений, предупреждения об отклонениях | `/notifications`, `/notifications/{id}/read` |
| Карточки «Безопасный интернет», «Роуминг», рекомендации | `/services?category=security`, `/services?category=roaming`, поле `recommendations` из `/dashboard` |

**Всего: 29 методов API.** Большинство экранов получает основные данные одним GET-запросом. Статические названия блоков, значки, календарная сетка и стили остаются на React-клиенте — отдельные endpoints для них не нужны.

## 3. Авторизация (6 методов)

### 3.1. `POST /auth/otp/request` — запрос SMS-кода

Публичный метод для входа по номеру или подтверждения номера при регистрации.

**Тело:**

```json
{ "phone": "+375291111111", "purpose": "login" }
```

`purpose`: `login` или `register`.

**Ответ `202`:**

```json
{ "status": "sent", "expires_in_seconds": 300 }
```

Сервер генерирует 6-значный код, сохраняет только HMAC-хеш в `auth_otps` и отправляет SMS через провайдера. Код действителен 5 минут, максимум 5 попыток; новый код отменяет предыдущий. Повторный запрос ограничивается (например, 1 раз в 60 секунд), частота запросов ограничивается по номеру и IP. Во избежание определения существующих аккаунтов метод возвращает одинаковый ответ независимо от регистрации номера. **В рабочем режиме код никогда не возвращается в JSON.** Для локальной отладки допускается mock-SMS-адаптер, который **только в режиме разработки** выводит код в консоль backend (не в HTTP-ответ) без отправки реальных сообщений.

### 3.2. `POST /auth/register` — регистрация

**Тело:**

```json
{
  "login": "demo_user",
  "password": "ExamplePassword123!",
  "full_name": "Иван Иванов",
  "email": "ivan@example.com",
  "phone": "+375291111111",
  "otp_code": "123456",
  "privacy_accepted": true
}
```

Все поля, кроме `email`, обязательны; `privacy_accepted` должно быть `true`. Код должен быть запрошен с `purpose=register`. Логин и номер уникальны. Пароль хешируется Argon2id. Сервер создаёт `users`, `subscribers`, назначает стартовый тариф `comfort-s`, формирует `account_number` и помечает OTP использованным **в одной транзакции**. При желании сервер может подключить стартовые бесплатные услуги из каталога; это настраивается в бизнес-логике, а не в frontend.

**Ответ `201`:**

```json
{
  "user": { "id": 1, "login": "demo_user", "full_name": "Иван Иванов" },
  "account": { "number": "+375291111111", "account_number": "2D2-000001" },
  "access_token": "<JWT>",
  "refresh_token": "<opaque-token>",
  "expires_in": 900
}
```

### 3.3. `POST /auth/login` — вход по логину и паролю

**Тело:**

```json
{ "login": "demo_user", "password": "ExamplePassword123!" }
```

**Ответ `200`:**

```json
{
  "access_token": "<JWT>",
  "refresh_token": "<opaque-token>",
  "expires_in": 900
}
```

Неверный логин/пароль: `401 INVALID_CREDENTIALS`. В БД хранится только хеш пароля. Access-токен живёт 15 минут, refresh-токен — 30 дней.

### 3.4. `POST /auth/otp/verify` — вход по номеру и коду

**Тело:**

```json
{ "phone": "+375291111111", "code": "123456" }
```

**Ответ `200`:** тот же объект токенов, что у `/auth/login`. Код должен иметь `purpose=login`, быть действующим и не использованным; по успешной проверке помечается использованным. Для неизвестного номера и неверного кода возвращается унифицированная ошибка.

### 3.5. `POST /auth/refresh` — обновление токенов

**Тело:** `{"refresh_token":"<opaque-token>"}`.

**Ответ `200`:** новая пара `access_token`, `refresh_token` и `expires_in`. Старый refresh-токен сразу отзывается (ротация). В `auth_sessions` хранится SHA-256 от refresh-токена, не его исходное значение.

### 3.6. `POST /auth/logout` — выход

**Тело:** `{"refresh_token":"<opaque-token>"}`.

**Ответ `204`:** пустое тело. Сессия помечается `revoked_at`; клиент удаляет оба токена. Уже выданный access-токен перестаёт действовать после истечения его короткого срока.

## 4. Профиль, номер и главная (4 метода)

### 4.1. `GET /me` — сведения об абоненте

**Ответ `200`:**

```json
{
  "user": {
    "id": 1,
    "login": "demo_user",
    "full_name": "Иван Иванов",
    "email": "ivan@example.com"
  },
  "number": {
    "id": 1,
    "msisdn": "+375291111111",
    "account_number": "2D2-000001",
    "nickname": "Мой номер",
    "is_blocked": false,
    "tariff_id": 1
  }
}
```

### 4.2. `PATCH /me` — редактирование профиля

**Тело (можно передать одно или оба поля):**

```json
{ "full_name": "Иван Петров", "email": "ivan.petrov@example.com" }
```

**Ответ `200`:** `{"user":{"id":1,"login":"demo_user","full_name":"Иван Петров","email":"ivan.petrov@example.com"}}`. Логин и телефон этим методом не меняются.

### 4.3. `PATCH /number` — управление номером

**Тело:**

```json
{ "nickname": "Рабочий", "is_blocked": false }
```

Оба поля необязательны, но минимум одно должно быть передано. Блокировка временно запрещает подключать новые услуги и потреблять трафик; разблокировка разрешена владельцу после авторизации. Настоящую SIM-блокировку выполняет операторская система, здесь сохраняется статус в кабинете.

**Ответ `200`:**

```json
{ "number": { "msisdn": "+375291111111", "nickname": "Рабочий", "is_blocked": false } }
```

### 4.4. `GET /dashboard` — данные главной страницы

В одном ответе передаются баланс, текущий тариф, количество услуг, остатки пакетов, безлимитные услуги, рекомендации и счётчики уведомлений. Текущий расчётный месяц определяется по `Europe/Minsk`.

**Ответ `200` (сокращённый пример):**

```json
{
  "balance_byn": "23.46",
  "balance_updated_at": "2026-10-29T12:00:00+03:00",
  "tariff": { "id": 1, "name": "Комфорт S", "monthly_fee_byn": "12.50" },
  "connected_services_count": 4,
  "traffic": {
    "internet": { "included_mb": 10240, "used_mb": 0, "remaining_mb": 10240 },
    "services": [
      {
        "service_id": 1, "name": "Безлимитный интернет до 5 Мбит/с",
        "metric": "internet_mb", "is_unlimited": true,
        "quota_amount": null, "used_amount": 0, "remaining_amount": null
      },
      {
        "service_id": 3, "name": "60 минут в другие сети",
        "metric": "minutes_other", "is_unlimited": false,
        "quota_amount": 60, "used_amount": 0, "remaining_amount": 60
      },
      {
        "service_id": 2, "name": "Безлимит на мессенджеры",
        "metric": "messenger_mb", "is_unlimited": true,
        "quota_amount": null, "used_amount": 0, "remaining_amount": null
      }
    ]
  },
  "recommendations": [
    { "type": "service", "id": 6, "title": "Звонки в роуминге", "tag": "popular" }
  ],
  "unread": { "alerts": 1, "messages": 2 }
}
```

Правила остатков: тарифный интернет = `tariffs.included_internet_mb` минус сумма `usage_events.quantity` для `metric=internet_mb` и `service_id IS NULL` за месяц. Для подключённого лимитного пакета берутся события по его `service_id` и `quota_metric`. Значение `remaining_amount` ограничивается снизу нулём. Для безлимита `remaining_amount = null`, `is_unlimited = true`. Рекомендации формируются из активных тарифов/услуг с `is_featured=true`, без отдельной таблицы баннеров.

## 5. Тарифы и услуги (4 метода)

### 5.1. `GET /tariffs` — каталог тарифов

**Ответ `200`:**

```json
{
  "items": [
    {
      "id": 1, "code": "comfort-s", "name": "Комфорт S",
      "description": "Базовый тариф с 10 ГБ интернета",
      "monthly_fee_byn": "12.50", "included_internet_mb": 10240,
      "is_current": true
    }
  ]
}
```

Выводятся активные тарифы и уже выбранный тариф (даже если он больше не продаётся).

### 5.2. `PUT /number/tariff` — сменить тариф

**Тело:** `{"tariff_id":2}`.

**Ответ `200`:** `{"tariff":{"id":2,"name":"Новый тариф","monthly_fee_byn":"19.90"},"effective":"immediately"}`.

Выбрать можно только активный тариф. Для учебного проекта изменение действует сразу; новое регулярное начисление появляется в следующем расчёте по правилам биллинга. Перерасчёт неполного месяца не выполняется (сознательное упрощение).

### 5.3. `GET /services` — подключённые и доступные услуги

**Параметры:**
- `status=connected|available|all` (по умолчанию `all`);
- `search` — необязательный поиск по названию и описанию;
- `category=internet|messengers|calls|security|roaming|other` — необязательный фильтр.

**Пример:** `GET /services?status=connected&search=безлимит`.

**Ответ `200`:**

```json
{
  "items": [
    {
      "id": 2,
      "name": "Безлимит на мессенджеры",
      "description": "Безлимитный трафик популярных мессенджеров",
      "category": "messengers",
      "monthly_fee_byn": "0.00",
      "quota_metric": "messenger_mb",
      "quota_amount": null,
      "is_unlimited": true,
      "is_connected": true,
      "connected_at": "2026-10-01T10:00:00+03:00"
    }
  ],
  "count": 1
}
```

`available` означает услугу, которую ещё не подключили. И подключённая, и доступная вкладки используют этот endpoint. Для не подключённой услуги `connected_at = null`.

### 5.4. `PUT /services/{id}/connection` — подключить/отключить услугу

**Тело:**

```json
{ "enabled": true }
```

`true` — подключить, `false` — отключить. Повторный запрос в том же состоянии не создаёт повторного подключения или начисления.

**Ответ `200`:**

```json
{
  "service_id": 2,
  "is_connected": true,
  "connected_at": "2026-10-29T14:30:00+03:00"
}
```

При подключении создаётся запись `subscriber_services` с `disconnected_at=NULL`. При отключении у активной записи проставляется `disconnected_at`; история не удаляется. Стоимость услуги попадает в `charges` при расчёте биллинга, а не при каждом повторном нажатии кнопки. Попытка подключить недоступную услугу или подключить её при заблокированном номере возвращает `409`.

## 6. Финансы (8 методов)

### 6.1. `GET /finance/summary` — финансовая сводка

**Ответ `200`:**

```json
{
  "balance_byn": "23.46",
  "current_month": "2026-10",
  "current_month_charges_byn": "31.36",
  "outstanding_invoices_byn": "0.00",
  "latest_invoice": { "id": 10, "period": "2026-09", "total_byn": "31.36" }
}
```

Используется на странице «Финансы» и для шапки финансовых карточек.

### 6.2. `GET /finance/charges` — начисления за месяц

**Параметр:** `month=YYYY-MM`, по умолчанию текущий месяц.

**Пример:** `GET /finance/charges?month=2026-10`.

**Ответ `200`:**

```json
{
  "month": "2026-10",
  "total_byn": "31.36",
  "items": [
    {
      "id": 101,
      "type": "tariff",
      "description": "Комфорт S",
      "amount_byn": "12.50",
      "vat_byn": "2.50",
      "total_byn": "15.00",
      "charged_at": "2026-10-01T00:00:00+03:00"
    }
  ]
}
```

`total_byn` = сумма `amount_byn + vat_byn` всех начислений периода. В текущем месяце записи могут ещё не быть привязаны к счёту (`invoice_id=NULL`).

### 6.3. `GET /finance/invoices` — счета за 12 месяцев

**Параметр:** `months` — целое число от 1 до 12, по умолчанию 12. Сортировка по периоду от нового к старому.

**Ответ `200`:**

```json
{
  "items": [
    {
      "id": 10,
      "period": "2026-09",
      "total_byn": "31.36",
      "paid_byn": "31.36",
      "due_byn": "0.00",
      "status": "paid",
      "issued_at": "2026-10-02T09:00:00+03:00"
    }
  ]
}
```

`due_byn = total_byn - paid_byn`. Статус вычисляется сервером: `paid`, `partially_paid` или `unpaid`. Незакрытый текущий месяц отображается в «Начисления», а не в выставленных счетах.

### 6.4. `GET /finance/invoices/{id}` — содержимое счёта

**Ответ `200`:**

```json
{
  "id": 10,
  "period": "2026-09",
  "total_byn": "31.36",
  "paid_byn": "31.36",
  "due_byn": "0.00",
  "status": "paid",
  "items": [
    { "type": "tariff", "description": "Комфорт S", "amount_byn": "12.50", "vat_byn": "2.50", "total_byn": "15.00" },
    { "type": "service", "description": "Дополнительные услуги", "amount_byn": "13.63", "vat_byn": "2.73", "total_byn": "16.36" }
  ]
}
```

Если счёт принадлежит другому абоненту, сервер отвечает `404`, а не раскрывает данные.

### 6.5. `GET /finance/payments` — история пополнений

**Параметр:** `months` — число от 1 до 12, по умолчанию 8.

**Ответ `200`:**

```json
{
  "items": [
    {
      "id": 45,
      "amount_byn": "20.00",
      "status": "succeeded",
      "created_at": "2026-10-20T11:00:00+03:00",
      "confirmed_at": "2026-10-20T11:01:00+03:00"
    }
  ]
}
```

В списке могут встречаться `pending` и `failed`. Только `succeeded` учитываются как поступившие деньги.

### 6.6. `GET /finance/usage-details` — детализация потребления

**Параметры:** `from=YYYY-MM-DD`, `to=YYYY-MM-DD`, `page` (по умолчанию 1), `limit` (по умолчанию 50, максимум 100). Диапазон — не более 3 лет. Обе границы дат включены.

**Пример:** `GET /finance/usage-details?from=2026-10-01&to=2026-10-29&page=1&limit=50`.

**Ответ `200`:**

```json
{
  "items": [
    {
      "id": 900,
      "occurred_at": "2026-10-28T15:12:00+03:00",
      "metric": "minutes_other",
      "quantity": 3.5,
      "unit": "min",
      "peer_number": "+375291234567",
      "service_id": 3,
      "cost_byn": "0.00"
    }
  ],
  "page": 1,
  "limit": 50,
  "total": 1
}
```

Для `internet_mb` и `messenger_mb` `unit="MB"`, для `minutes_*` — `unit="min"`. Источник — `usage_events`, только данные текущего абонента.

### 6.7. `POST /finance/topups` — начать пополнение

**Заголовок:** `Idempotency-Key: 6c8c4cf1-68ce-4c1c-809d-cdb47b4207e9`.

**Тело:**

```json
{ "amount_byn": "20.00" }
```

Разрешена положительная сумма, например от `1.00` до `1000.00` BYN (диапазон — конфигурация сервера). Сервер создаёт платёж со статусом `pending` и открывает платёжную сессию у провайдера. **Само обращение к этому endpoint не увеличивает баланс.**

**Ответ `201`:**

```json
{
  "payment_id": 45,
  "status": "pending",
  "checkout_url": "https://payments.example/checkout/opaque-reference"
}
```

`checkout_url` в примере условный: реальный URL возвращает подключённый платёжный провайдер. Повтор с тем же `Idempotency-Key` и той же суммой возвращает прежний платёж. С тем же ключом и другой суммой — `409`.

### 6.8. `POST /integrations/payment-webhook` — подтверждение платёжного провайдера

**Только для сервера провайдера, не для React-клиента.** Подлинность события проверяется по подписи провайдера (например, `X-Payment-Signature`) и его реальному формату. Нельзя принимать подтверждение оплаты от браузера.

**Нормализованное событие после проверки адаптером (пример):**

```json
{
  "event_id": "evt_5001",
  "provider_payment_id": "pay_45",
  "status": "succeeded",
  "amount_byn": "20.00",
  "currency": "BYN"
}
```

**Ответ `204`:** пустое тело. По подписанному событию `succeeded` сервер проверяет ID платежа, валюту и сумму, затем **атомарно** меняет статус `payments`, увеличивает `subscribers.balance_byn` и при наличии долга обновляет `invoices.paid_amount_byn`. Повторное событие не должно повторно зачислять деньги. Ошибочная подпись — `401/403`.

Для курсовой работы разрешён **mock-провайдер**, который выполняет этот же подтверждающий переход внутри тестовой среды. Не следует делать публичный endpoint вида «добавить деньги на баланс».

## 7. Аналитика (1 метод)

### 7.1. `GET /analytics` — все графики и календарь

**Параметры:** `month=YYYY-MM` (выбранный месяц, по умолчанию текущий), `months` (целое от 1 до 12, по умолчанию 6).

**Пример:** `GET /analytics?month=2026-10&months=6`.

**Ответ `200` (пример с сокращёнными массивами):**

```json
{
  "selected_month": "2026-10",
  "months_count": 6,
  "minutes_by_month": [
    { "month": "2026-09", "own": 95.0, "other": 38.0 },
    { "month": "2026-10", "own": 110.0, "other": 42.0 }
  ],
  "payment_distribution": {
    "total_byn": "31.36",
    "parts": [
      { "type": "tariff", "amount_byn": "19.76", "percent": 63.01 },
      { "type": "service", "amount_byn": "11.60", "percent": 36.99 }
    ]
  },
  "popular_services": [
    { "service_id": 1, "name": "Безлимитный интернет до 5 Мбит/с", "percent_connected": 80.0 },
    { "service_id": 2, "name": "Безлимит на мессенджеры", "percent_connected": 75.0 }
  ],
  "internet_by_day": [
    { "date": "2026-10-27", "used_mb": 180.0 },
    { "date": "2026-10-28", "used_mb": 320.5 }
  ],
  "calendar_activity_days": ["2026-10-27", "2026-10-28"],
  "unread_alerts": 1
}
```

**Как вычисляется аналитика:**

1. `minutes_by_month` — суммы `usage_events.quantity` по `minutes_own` и `minutes_other` за каждый месяц указанного окна. Пропущенные месяцы возвращаются с нулями.
2. `payment_distribution` — **структура начислений**, а не сумма банковских пополнений: сумма `(amount_byn + vat_byn)` из `charges`, сгруппированная по `charge_type`, за выбранный месяц. Для `usage` может быть третья часть. При нулевой сумме проценты равны нулю.
3. `popular_services` — процент абонентов, у которых услуга активна сейчас: количество уникальных `subscriber_id` с `disconnected_at IS NULL` / количество зарегистрированных абонентов × 100. Показываются наиболее популярные активные услуги (например, первые 3).
4. `internet_by_day` — объём `internet_mb` плюс `messenger_mb`, сгруппированный по датам выбранного месяца. Дни без потребления имеют значение 0 (сервер может возвращать полный календарный ряд).
5. `calendar_activity_days` — даты выбранного месяца, в которые были события из `usage_events`. React сам строит сетку календаря, выбор месяца и подсветку дат.
6. `unread_alerts` — количество непрочитанных `notifications` с `kind='alert'`.

Для оповещений об отклонениях биллинг/аналитический обработчик может создавать строки `notifications` при достижении 80–100% пакета, отрицательном балансе или необычном росте потребления. Это внутренняя логика сервера, новый публичный endpoint для её запуска не требуется.

## 8. Любимые собеседники (4 метода)

### 8.1. `GET /favorites` — список

**Ответ `200`:**

```json
{
  "items": [
    { "id": 1, "name": "Папа", "phone": "+375293091909" },
    { "id": 2, "name": "Мама", "phone": "+375296135907" }
  ]
}
```

### 8.2. `POST /favorites` — добавить контакт

**Тело:** `{"name":"Папа","phone":"+375293091909"}`.

**Ответ `201`:** `{"id":1,"name":"Папа","phone":"+375293091909"}`. Номер должен иметь формат E.164; дубликат номера в контактах одного абонента — `409`.

### 8.3. `PATCH /favorites/{id}` — изменить контакт

**Тело:** `{"name":"Папа (дом)","phone":"+375293091909"}`. Допускается передать только одно из полей.

**Ответ `200`:** `{"id":1,"name":"Папа (дом)","phone":"+375293091909"}`.

### 8.4. `DELETE /favorites/{id}` — удалить контакт

**Ответ `204`:** пустое тело. Все операции ограничены контактами текущего абонента.

## 9. Уведомления (2 метода)

### 9.1. `GET /notifications` — уведомления и сообщения

**Параметры:** `kind=alert|message|all` (по умолчанию `all`), `unread_only=true|false` (по умолчанию `false`). Для небольшого учебного кабинета достаточно последних 50 записей, отсортированных по `created_at DESC`.

**Ответ `200`:**

```json
{
  "unread": { "alerts": 1, "messages": 2 },
  "items": [
    {
      "id": 55,
      "kind": "alert",
      "title": "Заканчивается пакет интернета",
      "body": "Израсходовано более 80% включённого трафика",
      "target_path": "/services",
      "created_at": "2026-10-29T08:20:00+03:00",
      "is_read": false
    }
  ]
}
```

`alert` выводится за значком `!`, `message` — за конвертом. Счётчики берутся из всех непрочитанных уведомлений независимо от текущего фильтра.

### 9.2. `PATCH /notifications/{id}/read` — отметить прочитанным

Тело не требуется.

**Ответ `200`:** `{"id":55,"is_read":true}`. Повторное нажатие не меняет состояние; чужое уведомление возвращает `404`.

## 11. Важные правила реализации

**Регистрация и безопасность.** Телефон подтверждается SMS-кодом *до* создания учётной записи. Сервер не доверяет `subscriber_id`, суммам начислений и состоянию оплаты из браузера. Проверять владельца записей по `subscribers.user_id`. JWT подписывать серверным секретом/ключом, refresh-токены генерировать криптографически стойкими. Пароли хранить Argon2id; OTP — HMAC-SHA256 с серверным секретом. Для оператора действительных телефонных номеров регистрация должна подтверждать связь с уже выделенным абонентом; создание нового номера при регистрации допустимо только в учебной имитации.

**Учёт денег.** Изменение баланса, создание/изменение платежа и погашение счетов производятся транзакционно с блокировкой строки абонента (`SELECT ... FOR UPDATE`). Платёж сначала `pending`; баланс изменяется **только** после подлинного `succeeded` и только один раз. При выставлении счёта биллинг создаёт `invoices`, привязывает к нему `charges` и записывает итог; списывает доступную сумму с баланса, записывая её в `paid_amount_byn`. Недоплата отражается отрицательным балансом и `due_byn`. Успешное пополнение погашает неоплаченные счета по порядку от старых к новым, остаток остаётся на балансе. Все записи обрабатываются атомарно, чтобы `paid_amount_byn` и `balance_byn` не расходились. `total_amount_byn` должен точно равняться сумме строк `charges` с НДС. Двойные зачисления предотвращают проверка состояния `payments.status`, `provider_payment_id` и `idempotency_key`.

**Начисления и трафик.** Записи `usage_events`, `charges` и выставление `invoices` формирует внутренний процесс оператора/биллинга (или тестовый генератор данных). Пользовательских POST-методов для подделки потребления и начислений **нет**. Типовые внутренние задания: загрузить события потребления; начислить тариф и услуги на расчётный период; закрыть месяц; отправить уведомление о превышении порога. Они не требуют публичных REST endpoints. Для `quota_metric` конкретной услуги события должны содержать её `service_id`; базовый интернет тарифа учитывается с `service_id=NULL`.

**Простота реализации.** Справочники тарифов и услуг уже содержат начальные записи в SQL-файле. Пользователи, реальные платежи, SMS и данные потребления не подставляются как фиктивные успешные результаты. Если внешние SMS/платёжные системы недоступны, включается явно обозначенный **локальный учебный mock**, а не незащищённый способ обойти подтверждение. Реализация на Go/Node.js + PostgreSQL может использовать описанные маршруты без дополнительных таблиц и сервисов.
