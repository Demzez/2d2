# 2D2 — backend аналитического кабинета абонента

Самостоятельное HTTP-приложение на **Go 1.23+** и **PostgreSQL 15+**. Реализует все **29 методов** из `API_endpoints.md` под `/api/v1` на порту `5555`.

Не требуется Redis, отдельный планировщик, SMS-шлюз, платёжный провайдер или другой backend. Для локальной разработки SMS и подтверждение платежей заменены **явно отмеченными учебными адаптерами**. База PostgreSQL — единственный инфраструктурный компонент. React-клиент обращается к сервису по HTTP.

## Структура

```text
cmd/
  telecom/
    main.go                  # запуск и фоновый расчёт
    router.go                # маршруты и авторизация
  mock_payment/main.go       # локальная утилита подписанного webhook
internal/
  config/config.go           # конфигурация из переменных окружения
  object/errors.go           # типизированные HTTP-ошибки
  lib/logger/slog/slogpretty/slogpretty.go
  http_server/
    common/                   # JSON, параметры, обработка ошибок
    auth_handler/             # 6 методов авторизации
    cabinet_handler/          # чтение и изменение данных, 21 метод
    finance_handler/          # пополнение и webhook, 2 метода
  service/
    auth/                     # JWT, Argon2id, OTP и сессии
    cabinet/                  # валидация и логика личного кабинета
    finance/                  # безопасность и валидация платежей
  repository/postgres/
    repository.go             # подключение и общие методы
    auth.go                   # данные авторизации, транзакции
    cabinet.go                # профиль, услуги, контакты, уведомления
    finance.go                # финансы, статистика, биллинг, оповещения
sql/telecom_schema.sql       # схема БД и каталоги тарифов/услуг
API_endpoints.md             # исходный контракт API
.env.example                 # настройки для локального запуска
```

По образцу исходного Go-проекта: `handler → service → repository`, конструкторы `NewService` и `NewRepository`, методы `Get.../Change...` и `Read.../Update...`, единый `op` для контекста ошибок, `fmt.Errorf("%s | ... failed: %w", op, err)`. Репозиторий не пишет в лог, HTTP-уровень переводит ошибки в коды и обрабатывает логирование. Внутри репозитория используются параметризованные запросы и транзакции `database/sql`.

## 1. Подготовить PostgreSQL

Создайте пользователя и базу (в примере пароль учебный):

```bash
psql -U postgres -c "CREATE USER telecom WITH PASSWORD 'telecom';"
psql -U postgres -c "CREATE DATABASE telecom OWNER telecom;"
```

Перейдите в корень проекта и примените схему:

```bash
psql 'postgres://telecom:telecom@127.0.0.1:5432/telecom?sslmode=disable' \
  -v ON_ERROR_STOP=1 -f sql/telecom_schema.sql
```

По сравнению с предоставленной схемой добавлена **одна последовательность** `telecom.account_numbers_seq` для автоматической генерации `2D2-000001`, `2D2-000002` и т. д. Схема, таблицы, исходные тарифы и услуги сохранены. Скрипт можно безопасно запускать повторно, если данные уже существуют.

## 2. Настроить и запустить backend

```bash
cp ..env.example ..env
# Измените три секрета и пароль PostgreSQL перед запуском.
set -a
source ..env
set +a

go mod tidy
go run ./cmd/telecom
```

Команда `go mod tidy` один раз загрузит стандартные библиотеки Go-проекта из репозиториев модулей; при дальнейшем запуске сетевое обращение к другим сервисам не требуется. `.env` не загружается автоматически — переменные должны быть экспортированы в оболочке либо заданы в конфигурации запуска GoLand.

В GoLand откройте **папку проекта**, выполните Go Modules Download, создайте Run Configuration: Package `telecom/cmd/telecom` (или `go run ./cmd/telecom`) и укажите переменные из `.env`. Адрес API: **`http://127.0.0.1:5555/api/v1`**. Для React на другом порту поменяйте `ALLOWED_ORIGIN`.

`DEV_MODE=true` предназначен только для локальной разработки. По умолчанию сервер принимает соединения только на `127.0.0.1`. При `DEV_MODE=false` попытки использовать неподключённые SMS/платёжные интеграции завершаются ошибкой доступности — фиктивный ответ об успешной отправке или оплате не возвращается.

## 3. Зарегистрировать абонента

Запросите OTP:

```bash
curl -X POST http://127.0.0.1:5555/api/v1/auth/otp/request \
  -H 'Content-Type: application/json' \
  -d '{"phone":"+375291111111","purpose":"register"}'
```

В **консоли backend**, только при `DEV_MODE=true`, появится `[DEV MOCK SMS] ... : 123456`. Настоящих SMS нет, код не появляется в HTTP-ответе. Вставьте увиденный код в запрос регистрации:

```bash
curl -X POST http://127.0.0.1:5555/api/v1/auth/register \
  -H 'Content-Type: application/json' \
  -d '{"login":"demo_user","password":"ExamplePassword123!","full_name":"Иван Иванов","phone":"+375291111111","otp_code":"КОД_ИЗ_КОНСОЛИ","privacy_accepted":true}'
```

Регистрация создаёт пользователя, номер и счёт с тарифом `comfort-s` в одной транзакции. Access-токен действителен 15 минут, refresh-токен — 30 дней. Для остальных 22 приватных методов передавайте `Authorization: Bearer <access_token>`.

## 4. Работа платежей без внешнего провайдера

Создание платежа *не* пополняет баланс:

```bash
curl -X POST http://127.0.0.1:5555/api/v1/finance/topups \
  -H 'Authorization: Bearer ВАШ_ACCESS_TOKEN' \
  -H 'Content-Type: application/json' \
  -H 'Idempotency-Key: 6c8c4cf1-68ce-4c1c-809d-cdb47b4207e9' \
  -d '{"amount_byn":"20.00"}'
```

В mock-режиме возвращаются `payment_id`, `status: pending`, **`checkout_url: null`**: у локального адаптера нет внешней платёжной страницы. Это единственное осознанное отличие ответа от примера реального провайдера в `API_endpoints.md`. `payment_id` (например, `1`) используется далее. В отдельном терминале с тем же `PAYMENT_SECRET`:

```bash
go run ./cmd/mock_payment -id 1 -amount 20.00 -status succeeded
```

Эта **локальная CLI-утилита** сама формирует HMAC-SHA256 подписанное событие для *существующего* маршрута `POST /api/v1/integrations/payment-webhook`. Только корректное событие `succeeded` один раз увеличивает баланс и гасит долги; повторное событие безопасно. Утилита не создаёт дополнительный HTTP endpoint и не требует запущенного платёжного сервиса. Для проверки отказа укажите `-status failed`.

## 5. Биллинг, использование и аналитика

При запуске и затем ежечасно выполняется внутренний обработчик: создаёт начисления за текущий месяц, закрывает предыдущий расчётный месяц, проверяет отрицательный баланс и потребление 80% тарифного/подключённого лимита. Если база была отключена на границе месяца, обработчик создаёт недостающие начисления предыдущего месяца. Повторные вызовы не создают повторных начислений при неизменном тарифе и составе услуг. НДС принят **20%** в соответствии с примерами из API.

Тарифные суммы и услуги выставляются по текущему состоянию профиля; исторической смены тарифа в исходной схеме нет, поэтому полноценный операторский перерасчёт за произвольные прошлые периоды не моделируется. Для самостоятельной работы кабинета это учебное ограничение. Данные `usage_events` **не генерируются искусственно**: их можно импортировать через SQL (в рамках учебного эмулятора оператора). Если событий нет, графики и остатки корректно показывают нулевое потребление. Пользовательский API не позволяет создавать/подделывать события или начисления.

## Безопасность и особенности

- Идентификатор абонента берётся только из проверенного JWT, а не из параметров React. Владелец проверяется в SQL для каждого счёта, платежа, контакта, услуги и уведомления.
- Пароли: Argon2id; OTP: HMAC-SHA256 и максимум пять попыток; refresh-токены: SHA-256 в БД и ротация; JWT: HS256. Повторный OTP не ранее 60 секунд, дополнительно до 20 запросов/час с одного IP в памяти процесса.
- Все суммы передаются строками с двумя десятичными знаками; операции платежей ведутся в копейках, а SQL-начисления — в `NUMERIC(12,2)`. Расчётный месяц определяется по `Europe/Minsk`.
- Пополнение и выставление счета транзакционны. Дополнительные фоновые сервисы отсутствуют.
- HTTP-ответы об ошибке имеют вид `{"error":{"code":"...","message":"..."}}`. Пароли, refresh-токены и секреты не передаются в логирование.
- Схема отражает модель личного кабинета, **не** управляет реальной SIM-картой и не обращается к сетевой инфраструктуре оператора. Для реального оператора потребовались бы внешние SMS/платёжные адаптеры и источник CDR/трафика.
